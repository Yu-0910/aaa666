# 投手個人ページ「今季の成績」見出し実装計画

## 目的

`app/players/[playerId]/page.tsx` にある投手用「今季の成績」（菅野シェル：4 サブタブ）の **各見出しブロック**を、実データで埋める。  
現時点のデータは **2026年3月27日 広島対中日 1試合分**（canonical / 派生 JSON）に限定されるため、**当該試合に登板した広島・中日の投手**の個人ページにのみ数値が入り、それ以外の投手は従来どおり「—」「ー」または説明文でよい（仕様として明記する）。

## スコープ外（本書では扱わない）

- **通算タブ**の「キャリアハイの打撃成績」「通算の打撃成績」は、現状すべての選手で打撃用ダミー表示。投手専用の通算投球は **別計画**とする（本計画の Phase には含めない）。
- ランキングページ・R2 配信は対象外。

実装単位は「サブタブ × `h2` 相当のブロック」。タブラベルも下表に含める。

## データ前提（PoC）

| 項目 | 内容 |
|------|------|
| 試合 | 2026-03-27 広島 vs 中日（プロジェクト内の canonical / `yahooGameId` と整合させる） |
| 対象選手 | 名簿上 **投手**かつ、当該試合のイベントに **その投手の投球**が存在する選手 |
| 表示上の「今季」 | 1 試合のみの集計であることを、必要なら脚注やツールチップで明示（誤解防止） |

---

## Phase 0 — 前提の固定（短時間・単独）

**やること**

- 対象 `game_id` / `yahooGameId` をドキュメントとコードの既定値で一致させる（広島中日戦）。
- 広島・中日の投手について `npb_player_id` → 試合内投手としての出現 の対応を検証（マップ欠けは CSV または手当てリストで補完）。

**完了条件**: 上記試合の canonical から「登板投手一覧」を機械的に列挙できる。

**一括に含めない理由**: 以降の Phase の入力仕様を先に固める必要があるため、短いゲートとして独立。

---

## Phase 1 — イベント単体で完結する集計（一括パイプライン）

**実装スクリプト**: `scripts/phase_pitcher_poc1_build_from_canonical.ts`  
**実行**: `npm run phase:pitcher-poc1`（既定 `--year 2026`）

**方針**: canonical（打席・投球イベント、結果テキスト等）**だけ**から再計算できる指標を、**1 本の生成スクリプト**（または 1 コマンドで連続実行するターゲット）で `_data/derived/player_season_pitching_poc/{year}/npb_{id}.json` のように出力する。

**本 Phase で一括して埋める見出し（データソース共通）**

| 見出し | 備考 |
|--------|------|
| 基本成績（3 表） | 1 試合分の防御率・回数・被安打・三振・四死球・失点・自責等。先発/救援・勝敗・H/QS 等は **定義どおり取れるもののみ** 埋め、取れないセルは「—」。 |
| 対チーム別の投球成績 | **対戦相手（広島 or 中日の相手側）の 1 行のみ**実値。他 11 球団は「—」。 |
| 左右別の投球成績 | 打者左右別に集計。 |
| 状況別の投球成績 | ランナー状況（無し・1塁…）は、野手ページの状況別と **同一の状態機械・定義**に寄せる（既存 `paSituation` 系を流用可能なら流用）。 |
| イニング別の投球成績 | 1〜9 回（登板しなかった回は「—」）。 |
| 投球指標（一部） | 被打率・被出塁率・WHIP・K%・BB%・K-BB%・被長打率・HR/9 等、**イベントから定義できるもの**。HQS/SQS・RSAA・援護率等は **Phase 8** へ回すか本 Phase では常に「—」。 |

**完了条件**: 上記 JSON が対象投手分生成され、スキーマが API で返せる形に固定される。

**一括にした理由**: 入力は canonical の同一パス、差分は集計キー（チーム／左右／状況／イニング）だけのため、分割すると二重実装になりやすい。

---

## Phase 2 — API と UI の一括結線（基本・状況タブの「イベント由来」部分）

**実装**: `GET /api/players/[playerId]/season-pitching?year=2026`（`lib/pitcherSeasonPocLoad.ts` で `_data/derived/player_season_pitching_poc/...` を読込）。`app/players/[playerId]/page.tsx` の投手「今季」で取得し、基本・対チーム・左右・状況別・イニング・投球指標（一部）・球種/ゾーン用の既定 `yahooGameId`（canonical の先頭 gameId）に結線済み。

**やること**

- `GET /api/players/[playerId]/season-pitching`（名称は実装で調整）で Phase 1 の JSON を返す。`playerId` は既存個人ページと同じ公開 ID。内部で `npb_player_id` に解決。
- `page.tsx` の **基本成績・対チーム別・左右別・状況別（ランナー表）・イニング別・投球指標（Phase 1 で埋まる列）** をプレースホルダーから置換。

**完了条件**: 広島・中日の対象投手で、上記ブロックに 1 試合由来の数値が表示される。他投手は従来どおり。

**Phase 1 と一括にしなかった理由**: 生成物の検証と、HTTP/ fs の読み分けを分けた方がデバッグしやすい。

---

## Phase 3 — 球種情報タブ（既存 API 延伸・一括）

**やること**

- 既存 `/api/games/{gameId}/pitchers/npb/{npbId}/pitch-types` を、広島中日戦を既定 `gameId` としたときに **対象投手全員**で解決できるようにする（マップ・ファイル配置の不足を埋める）。
- 「球種一覧」表の **被OPS** 列など、データが揃えば埋める（無理なら「—」のまま明記）。
- `PitchTypePieChart` は既存のままデータ供給を安定化。

**完了条件**: 球種情報タブが Phase 0 の対象投手で一貫して表示（試合 ID のハードコード依存を減らす）。

**一括にした理由**: データソースは「試合×投手の球種 JSON」で共通。

---

## Phase 4 — コース別（ゾーン・一括）

**やること**

- 既存 `/api/games/.../zone-stats`（および `page.tsx` の `zoneStats` 取得ロジック）を、Phase 0 の試合・NPB 投手 ID で **対右／対左**とも取得可能にする。
- 「コース別の投球成績（対右打者／対左打者）」を実データで埋め、未取得時は従来の「ー」表示。

**完了条件**: 対象投手で 5×5 グリッドに数値が入る（少なくとも PoC 試合で 1 人以上確認）。

**Phase 3 とまとめられるか**: どちらも「試合×投手」の派生ファイル依存。チームが小さければ **Phase 3+4 を 1 Phase** にまとめてもよい。分ける場合は「球種」と「ゾーン」のファイル形式・API が異なるための分離。

---

## Phase 5 — メタデータ依存（分離：球場・ホーム/ビジター・デー/ナイター）

**前提**: canonical または試合メタに **球場名／主催（ホーム側）／デー・ナイター** が載る。無い場合は **Phase 2 のスキーマ拡張 or 試合マスタ JSON** を先に追加する必要がある（本 Phase のブロッカー）。

**見出し**

- 球場別の投球成績（1 試合なら **該当球場の 1 行のみ**実値、他行は「—」）
- ホーム&ビジター別の投球成績（**ホーム or アウェーの 1 行**）
- デー&ナイター別の投球成績（**デー or ナイターの 1 行**）

**一括に含めない理由**: 入力が「イベントログ」ではなく **試合メタ**に依存。メタが無い場合は実装を進められない。

---

## Phase 6 — 捕手別（分離）

**前提**: 各投球または各打席に **捕手の選手 ID** が紐づく。canonical に無い場合は、スクレイプ／正規化の拡張が先。

**見出し**: 捕手別の投球成績（1 試合なら捕手が複数いれば複数行、1 人なら 1 行）。

**一括に含めない理由**: データ項目の有無が他 Phase と独立してブロッカーになりやすい。

---

## Phase 7 — 期間別タブ（分離）

**見出し**

- 月間別の投球成績（例: 2026年3月のみ実値、他月は「—」）
- 週間別の投球成績（**週境界の定義**を野手の週間集計 `phase17` と揃える）

**一括に含めない理由**: カレンダー境界・タイムゾーン（JST）のポリシーが必要。1 試合でも「どの週ラベルに載せるか」を決める作業が独立。

---

## Phase 8 — 高度指標・記録系（分離・任意）

**見出しに対応する残セル**

- 投球指標のうち **HQS率・SQS率・FIP・LOB%・RSAA・RSWIN・援護率・IPR・NHB 系・PR/KD・失点時回数・救援時系** など、**リーグ平均・定義式・複数試合が前提**になりやすいもの。

**方針**: 1 試合 PoC では **「—」のまま**でもよい。埋める場合は指標ごとに定義書と係数（FIP 定数等）を決めてから実装。

**一括に含めない理由**: 指標ごとに定義・データ要件が異なり、1 本のスクリプトに混ぜると検証コストが高い。

---

## 実行順の推奨

1. Phase 0 → Phase 1 → Phase 2（**ここまでで「基本〜状況のコア」が動く**）
2. Phase 3 → Phase 4（試合×投手の詳細ログ系）
3. メタが揃い次第 Phase 5、捕手 ID が揃い次第 Phase 6
4. Phase 7（期間）
5. Phase 8（必要になった指標から順次）
