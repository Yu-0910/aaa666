# 重複選手URL変更 本番反映計画書

目的: 同姓同名または同一ローマ字変換により個人ページURLが衝突している選手について、重複時のみURLを分岐し、最終的に `short-stop.jp` 本番で正しく反映される状態まで到達する。

対象例:

- `やまもとこうじ` 系
- 現役名簿と historical が同一 slug を共有しているケース
- historical 同士で同一 slug を共有しているケース

非目的:

- 全選手URL体系の全面刷新
- 非重複選手のURL変更
- 個人ページUIの変更
- 成績データや表示項目の改修

## 基本方針

- URL変更は **重複時だけ** に限定する
- 非重複 slug は既存のまま維持する
- 既存の bare slug は可能な範囲で後方互換を残す
- 実行時に全件探索しない
- 重複解決結果は固定データとして管理する
- 本番反映の確認は、コード push だけで終わらせず、デプロイ先と公開URLを必ず確認する

## 成功条件

- 重複選手が別URLへ安定して分岐する
- サイト内リンクが該当選手の正しいURLを生成する
- 本番 `short-stop.jp` で変更後URLが確認できる
- 本番が `Yu-0910/aaa666` の反映を見ていることを確認できる
- 変更が非重複選手や既存UIに波及していない

## リスク

- Vercel の接続先リポジトリが別 repo になっている
- push 先ブランチと本番デプロイ対象ブランチが異なる
- historical slug の衝突一覧が未固定で、更新のたびに挙動が揺れる
- bare slug の後方互換が別選手へ誤誘導する
- 本番キャッシュにより反映確認を誤る

## Phase 1: 衝突対象の抽出

目的: どの選手がURL衝突しているかを確定する。

作業内容:

- roster と historical の slug 一覧を収集する
- 同一 slug を複数 `npbPlayerId` が共有しているケースを抽出する
- 現役 vs historical、historical vs historical を分類する
- 代表確認ケースとして `kouji-yamamoto` などを決める

完了条件:

- 分岐対象の `npbPlayerId` 一覧が確定している
- どの slug が何件衝突しているか説明できる

## Phase 2: URL分岐仕様の固定

目的: 重複時に採用するURL形式を決める。

作業内容:

- 非重複: 既存 slug を維持する
- 重複: `{baseSlug}-{npbPlayerId}` を採用する
- bare slug をどの選手へ解決するか後方互換方針を決める
- サイト内リンクは `npbPlayerId` 優先で正しい分岐 slug を返す方針にする

完了条件:

- URL命名規則が一意に決まっている
- bare slug の扱いを説明できる

## Phase 3: URL解決ロジックの実装

目的: 選手URL生成とURL解決に分岐仕様を反映する。

作業内容:

- historical override に一意 slug を反映する
- `playerPagePathSegmentKnown` などのリンク生成が `npbPlayerId` 優先で分岐 slug を返すようにする
- slug 解決側で新URLを正しく解決できるようにする
- bare slug と legacy slug を最低限の後方互換として維持する

完了条件:

- 同一 slug 衝突ケースで別々のURLが生成される
- 変更が既存UIや非重複選手に波及していない

## Phase 4: 重複解決結果の固定データ化

目的: 実行時の重複探索をやめ、結果を固定マップとして管理する。

作業内容:

- 重複対象の `npbPlayerId -> disambiguated slug` 対応表を生成する
- 生成済みファイルを `lib` 配下に追加する
- 実行時は生成済みマップ参照だけに置き換える
- 必要なら再生成手順を別途文書化する

完了条件:

- 実行時に全件カウントや全件比較をしていない
- 固定マップだけで重複URL解決が成立する

## Phase 5: ローカル検証

目的: 本番へ出す前に代表ケースの正しさを確認する。

確認項目:

- `kouji-yamamoto` 系が別URLになる
- `masahiro-tanaka` のような現役/historical 衝突が分離される
- 非重複選手のURLが変わっていない
- 既存ページで選手名、タブ、UIが壊れていない
- bare slug が想定どおりの選手へ到達する

完了条件:

- 代表重複ケースの URL 生成と URL 解決を説明できる
- ローカルで重大な退行がない

## Phase 6: Git 反映

目的: 変更を commit / push 可能な状態にする。

作業内容:

- 変更ファイルだけを commit する
- ブランチ名と push 先を明示する
- `origin` へ push する
- 必要に応じて本番反映用ブランチへ取り込む

完了条件:

- 対象 commit SHA を特定できる
- `origin` 上に反映対象 commit が存在する

## Phase 7: 本番デプロイ経路の確認

目的: push 後に本番が変わらない事故を防ぐ。

作業内容:

- Vercel の接続先リポジトリが `Yu-0910/aaa666` か確認する
- 本番デプロイ対象ブランチを確認する
- 対象 commit がそのデプロイ経路に含まれているか確認する
- 必要なら手動デプロイまたは本番ブランチ反映を行う

完了条件:

- 本番が見ている repo / branch を説明できる
- 反映対象 commit が本番デプロイ対象に乗っている

## Phase 8: 本番確認

目的: `short-stop.jp` 上で実際に反映されたことを確認する。

確認対象:

- 代表ケース 1: `kouji-yamamoto` 系
- 代表ケース 2: 現役/historical 衝突ケース
- 代表ケース 3: 非重複選手

確認内容:

- 該当選手リンクから正しい個人ページへ遷移する
- 直接URLを開いて正しい選手ページが表示される
- 404 や別人ページ遷移が起きない
- UI崩れがない

完了条件:

- 本番URLで変更後挙動を確認済み
- 反映なしの場合、どの段階で止まっているか切り分け済み

## Phase 9: 運用固定

目的: 次回以降も同種の修正を一発で本番反映しやすくする。

作業内容:

- 重複 slug 再生成手順を明文化する
- 本番反映チェックリストに Vercel 接続先確認を追加する
- push 後に見るべき本番確認URLを残す
- bare slug 後方互換方針を文書化する

完了条件:

- 次回の重複URL修正で迷う工程が減っている
- 実装と本番反映のチェック順が定義されている

## Phase 一覧

- Phase 1: 衝突対象の抽出
- Phase 2: URL分岐仕様の固定
- Phase 3: URL解決ロジックの実装
- Phase 4: 重複解決結果の固定データ化
- Phase 5: ローカル検証
- Phase 6: Git 反映
- Phase 7: 本番デプロイ経路の確認
- Phase 8: `short-stop.jp` 本番確認
- Phase 9: 運用固定

## 補足

- 2026年8月25日時点で、重複時のみ `-npbPlayerId` を付与する方針は実装済み
- 今後の主要論点は、どの commit をどの repo / branch / Vercel project 経路で本番へ届けるかに寄る
- そのため本計画では、コード修正そのものと同じ重さで **本番反映経路の確認** を扱う
