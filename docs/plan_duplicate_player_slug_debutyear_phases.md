# 重複選手URL変更 `slug-debutyear` 計画書

目的: 同姓同名または同一ローマ字変換により個人ページURLが衝突している選手について、重複時のみ `slug-debutyear` 形式でURLを分岐し、最終的に `short-stop.jp` 本番で安定反映される状態まで到達する。

対象例:

- `やまもとこうじ` 系
- 現役名簿と historical が同一 slug を共有しているケース
- historical 同士で同一 slug を共有しているケース
- 現在 `-npbPlayerId` で分岐している重複選手URL

非目的:

- 全選手URL体系の全面刷新
- 非重複選手のURL変更
- 個人ページUIの変更
- 成績データや表示項目の改修
- NPB公式のID体系を想起させる表現の採用

## 基本方針

- URL変更は **重複時だけ** に限定する
- 非重複 slug は既存のまま維持する
- 重複時は `slug-debutyear` を第一URLとする
- `debutYear` が取れない、または同年重複するケースの補助方針を先に固定する
- 実行時に全件探索しない
- 重複解決結果は固定データとして管理する
- 既存 `-npbPlayerId` URL は移行期間中の後方互換候補として扱う
- 本番反映の確認は、コード push だけで終わらせず、デプロイ先と公開URLを必ず確認する

## 成功条件

- 重複選手が `slug-debutyear` で安定して分岐する
- サイト内リンクが該当選手の正しいURLを生成する
- 既存の `-npbPlayerId` URL から新URLへ破綻なく到達できる
- 本番 `short-stop.jp` で変更後URLが確認できる
- 変更が非重複選手や既存UIに波及していない

## リスク

- `debutYear` の元データが欠損している
- 初出場年が同一の同名選手が存在し、`slug-debutyear` だけでは一意にならない
- 既存の `-npbPlayerId` URL を外すと、外部リンクや検索結果が壊れる
- Vercel の接続先リポジトリや本番ブランチが作業対象とずれている
- 本番キャッシュにより反映確認を誤る

## Phase 1: 現状棚卸し

目的: 現在の `-npbPlayerId` 方式と重複対象を整理し、移行対象を確定する。

作業内容:

- 現在の重複 slug 一覧を再取得する
- `slug -> npbPlayerId -> 現行URL` の対応を棚卸しする
- 現役 vs historical、historical vs historical を分類する
- 代表確認ケースとして `kouji-yamamoto` などを決める

完了条件:

- `slug-debutyear` へ切り替える対象一覧が確定している
- 現行URLと移行後URLの対応表を作れる

## Phase 2: `debutYear` ソース確定

目的: URLに使う初出場年の定義と取得元を固定する。

作業内容:

- `debutYear` の候補データ源を洗い出す
- 「NPB初出場年」を使うのか、「在籍初年度」を使うのかを固定する
- historical データで全対象の `debutYear` が取得可能か確認する
- 欠損時の補完方針を決める

完了条件:

- `debutYear` の意味が一意に決まっている
- 全重複対象に対して取得可否を説明できる

## Phase 3: 衝突再判定仕様の固定

目的: `slug-debutyear` でも重複する場合の扱いを先に決める。

作業内容:

- `slug-debutyear` の全候補を生成して再衝突有無を確認する
- 同一年重複がないか確認する
- 同一年重複がある場合の補助ルールを決める
- bare slug をどの選手へ解決するか後方互換方針を更新する

完了条件:

- URL命名規則が一意に決まっている
- 再衝突時のフォールバックルールを説明できる

## Phase 4: 固定マップ設計

目的: 実行時の探索をやめ、最終URLを固定データとして管理できる形にする。

作業内容:

- `npbPlayerId -> slug-debutyear` 対応表の生成仕様を定める
- bare slug alias と旧 `-npbPlayerId` alias の扱いを整理する
- 生成済みファイルの置き場と再生成手順を決める
- 後方互換に必要な alias 解決マップを設計する

完了条件:

- 実装前に必要な固定データ構造が決まっている
- 再生成の責務が曖昧でない

## Phase 5: URL生成・解決ロジック改修

目的: サイト内リンクと直接URL解決を `slug-debutyear` 方式へ切り替える。

作業内容:

- historical override に新URLを反映する
- `playerPagePathSegmentKnown` などのリンク生成を新方式へ切り替える
- `slug-debutyear` と bare slug を正しく解決できるようにする
- 既存 `-npbPlayerId` URL からも同じ選手へ到達できるようにする

完了条件:

- 重複選手で新URLが生成される
- 旧URLを開いても別人化しない

## Phase 6: 固定データ生成

目的: `slug-debutyear` と互換 alias の生成結果を確定させる。

作業内容:

- 生成スクリプトまたは手順で固定マップを出力する
- 対象全件の `slug`, `debutYear`, `finalSlug` を検証する
- 同一年重複や欠損年がある場合は例外テーブルへ反映する
- 出力結果をレビューし、代表ケースを控える

完了条件:

- 実行時に全件カウントや全件比較をしていない
- 固定マップだけでURL解決が成立する

## Phase 7: ローカル検証

目的: 本番へ出す前に代表ケースと互換導線の正しさを確認する。

確認項目:

- `kouji-yamamoto` 系が `slug-debutyear` へ分岐する
- 現役/historical 衝突が分離される
- 非重複選手のURLが変わっていない
- 旧 `-npbPlayerId` URL でも正しい選手へ到達する
- 既存ページで選手名、タブ、UIが壊れていない

完了条件:

- 代表重複ケースの URL 生成と URL 解決を説明できる
- ローカルで重大な退行がない

## Phase 8: Git 反映

目的: 変更を commit / push 可能な状態にする。

作業内容:

- 変更ファイルだけを commit する
- ブランチ名と push 先を明示する
- `origin` へ push する
- 必要に応じて本番反映用ブランチへ取り込む

完了条件:

- 対象 commit SHA を特定できる
- `origin` 上に反映対象 commit が存在する

## Phase 9: 本番デプロイ経路の確認

目的: push 後に本番が変わらない事故を防ぐ。

作業内容:

- Vercel の接続先リポジトリが対象 repo か確認する
- 本番デプロイ対象ブランチを確認する
- 対象 commit がそのデプロイ経路に含まれているか確認する
- 必要なら手動デプロイまたは本番ブランチ反映を行う

完了条件:

- 本番が見ている repo / branch を説明できる
- 反映対象 commit が本番デプロイ対象に乗っている

## Phase 10: 本番確認

目的: `short-stop.jp` 上で実際に反映されたことを確認する。

確認対象:

- 代表ケース 1: `kouji-yamamoto` 系
- 代表ケース 2: 現役/historical 衝突ケース
- 代表ケース 3: 非重複選手
- 代表ケース 4: 旧 `-npbPlayerId` URL の互換ケース

確認内容:

- 該当選手リンクから正しい個人ページへ遷移する
- 直接URLを開いて正しい選手ページが表示される
- 旧URLで 404 や別人ページ遷移が起きない
- UI崩れがない

完了条件:

- 本番URLで変更後挙動を確認済み
- 反映なしの場合、どの段階で止まっているか切り分け済み

## Phase 11: 運用固定

目的: 次回以降も同種の修正を一発で本番反映しやすくする。

作業内容:

- `slug-debutyear` 再生成手順を明文化する
- `debutYear` 欠損時の補完ルールを文書化する
- 旧 `-npbPlayerId` URL をいつまで残すか決める
- push 後に見るべき本番確認URLを残す

完了条件:

- 次回の重複URL修正で迷う工程が減っている
- 実装と本番反映のチェック順が定義されている

## 補足

- 2026年8月27日時点で、本番は重複時のみ `-npbPlayerId` を付与する方式で運用されている
- 今回はそれを `slug-debutyear` へ置き換える移行案件として扱う
- そのため、新URLの実装だけでなく、旧URLの後方互換と本番デプロイ経路の確認を同じ重さで扱う
