## 公式記録との差が出る主な理由（設計・取得）

1. **データソース**: 集計は **Yahoo!スポーツナビの一球速報テキスト／詳細ページ**由来。NPB の **公式確定成績 API には非依存**。試合後の訂正・公式のみの表記変更は自動では追従しない。
2. **略記パターン**: `hitBases` / `isAtBat` は **正規表現の列挙**。新しい略語・表記ゆれは **未マッチだと安打 0・打数のみ**などになる（上記 `内安` が典型）。
3. **同一ロジックの複製（解消済み）**: Phase11/12 の正は `canonicalBattingSeasonAgg.ts` の `updateBattingAggFromPa`（内部で `resultJaHitBases`）。**Phase13〜17 のスプリット集計も同関数を使用**するよう統一した。投手側 PoC は `pitcherPaResultCommon.ts` も `resultJaHitBases` を参照。
4. **未実装（ドキュメント §6）**: 打点・得点・盗塁などは PA からは加算していない。`result` が空・「ボール」のみ等は不整合の可能性。

## 6a. 打席中イベントと「投球表の分割」（情報取得ルール）

### `paId` と Yahoo `bat_order`（打順と混同しない）

- canonical の **`paId` 末尾**および Phase10 行の **`bat_order`** は、**半回内の打席通し番号**（実況の `N：`、score `index` の N）。**スタメン打順（1〜9番）ではない**。
- 定義の SSOT: `lib/yahooGame/paIdFormat.ts`。運用: `docs/data_operation_rules.md` §一球速報。
- 誤解例: `…-4-表-6` を「6番打者」と読むと、別打席の HR（`…-4-表-2` の 6番・外崎）と取り違える。

### 背景

Yahoo の一球詳細（`/game/{id}/score?index=...`）では、打席が完了する前に **走者・配球・捕手・審判**などの出来事が挟まると、**同一打席の続き投球が別ブロック**（別の `bb-splitsTable`）に出ることがある。  
旧実装のように **先頭の投球表だけ**を読むと、**決着球の行が欠ける**（最終行が中間イベントの `ボール[…]` のままになる等）。

`mergePhase10IntoCanonical`（`lib/yahooGame/mergePhase10FromPitchRows.ts`）は **`resultSummaryJa` = その打席の最終行の `result`** であるため、**取得で行が欠けると集計が必ずずれる**（安打・打数・三振など）。これは **正規表現の列挙**では直せず、**パイプライン側の取り込み**が正である。

**`yahooPitcherId`（打席レベル）**: Phase10 マージでは従来どおり **先頭行の `pitcher_id`** を載せる（出場成績との互換）。**対左右**は `yahooPitcherIdForVsHandFromPa` が `pitchEvents` を **配列の末尾から**走査し、非空の `yahooPitcherId` を優先する（`pitchIndex` 再ソートは順序事故のため行わない）。

**投球腕の解決**: Yahoo 投手 ID が NPB 橋渡しに無い場合でも、`game.yahooPlayersMentioned` の表示名で名簿照合し R/L を付ける（`pitcherThrowHandRLFromYahooPitcherIdWithMentioned`）。phase13 と phase15 で同一にする。

### 区切りの典型例（表記に現れやすいもの）

次のような **走者・配球・死球**のイベントは、ランエンドヒットと同様に **表示が一度区切られ、続きが別表**になり得る（すべてを網羅したものではない）。

| 区分 | 例（UI・結果テキストに現れやすい語） |
|------|--------------------------------------|
| 得点・進塁 | **ランエンドヒット**、**エンドラン**、スコアリングの補足（送球が逸れる・エラー絡み等） |
| 暴投・パスボール | **暴投**、**パスボール**、走者進塁と打席継続 |
| 牽制・走死 | **牽制**、**牽制死**、**けん制**（表記ゆれ） |
| 盗塁 | **盗塁**、**盗塁成功**、**盗塁失敗**、**盗塁死**（セーフ・アウトいずれも区切りを挟むことがある） |
| その他の走者プレー | **バッテリー**絡みの送球、走者の進塁・退塁の補足が長い行 |

### その他、分割や欠行が疑われる状況

- **投手交代**（打席途中でマウンドへ）
- **タイム**、**リプレイ審査**、**負傷**、**妨害** などの試合の一時停止
- **表記の都合**: 中間の一球が `ボール[ランエンドヒット…]` のように **状況説明だけ**が付き、**決着（ゴロ・飛・三振等）が次の表**にだけ出る

### 実装ルール（必須）

1. **スクレイピング**（`scripts/scrape_yahoo_pitch_details.py` の `parse_pitch_details`）  
   - 同一ページ内の **同一ヘッダ（球種・球速・結果）の `bb-splitsTable` をすべて、DOM 順に結合**してから行を並べる。  
   - **先頭の表だけ読んで `break` しない**（上記いずれのイベントでも同じルール）。
2. **ゾーンコース**  
   - 同一打席に複数の `allocationChart` がある場合、**打席通しの連番**で球と座標を対応付ける（球番が 1 からやり直すチャートにも対応）。
3. **canonical マージ後の検証の目安**  
   - 一球 UI で「区切りのあとに続く表」がないか確認する。  
   - 疑わしい打席は **Phase10 再取得** → `npm run phase4:merge:phase10:all`（または運用のマージ手順）で canonical を更新する。

### 「次行を見続ける」補正ルール（打席境界必須・仕様メモ）

**目的**: 詳しい投球表の **最終行**が **`ボール`** や **`ボール[…]`** など、**打席の決着として不十分な表記**（成績上の最終結果の短い表記ではない中間表記）に見える場合に、**同一打席の範囲だけ**後続行を参照し、**`resultSummaryJa` に使う行**を特定するためのルール案。  
※ **実装の有無にかかわらず**、パイプライン・コードレビューで「無条件に次行をマージしない」ための共通前提として置く。

**実装（マージ時・一部）**: `lib/yahooGame/mergePhase10FromPitchRows.ts` の `pickResultSummaryJaFromPitchRows`  
- 末尾が **`ボール`** または **`ボール[` で始まる**行だけを、**同一打席の投球行配列の末尾から逆方向に**取り除き、残った最後の行の `result` を `resultSummaryJa` に使う。  
- **HTML に決着行が無い**（例: 桑原打席で一ゴロ行が欠けている）場合は **要約は直せない**。  
- **2アウト・盗塁失敗で攻守交替**したあとの **相手イニング先頭打者**は、`inning|表裏|打順` が変わるため **別打席キー**となり、当該配列には含まれない（誤結合しない）。

1. **同一打席の定義（スキャン許可範囲）**  
   - 参照してよい「次の行」は、**同一 `game_id`・同一イニング・同一表裏・同一打順（`bat_order`）** に属する行（または DOM 上で当該打席ブロック内と明確に判定できる行）に限る。  
   - **イニングまたは表裏が変わった時点でスキャンを打ち切る**（次の半イニングに入ったとみなす）。

2. **「次の行は別打席／別チームのイニング」になり得る典型**  
   - **2 アウトのあと盗塁失敗（走者アウト）などで三人アウト**となった場合、記録上はその攻撃が終了し、**続く表示は相手チームのイニングの先頭打者**になり得る。  
   - この **相手イニング先頭打者の行を、直前の打席の「続きの球」として結合してはならない**（打席境界の誤認は致命的）。

3. **停止条件の例（実装時のチェックリスト）**  
   - 行に紐づく **投手 ID・打者 ID**（`#gm_rslt` 等）が、当該打席開始時の `pitcher_id` / `batter_id` と一致しなくなったとき。  
   - **投球番号が 1 に戻った**表・行（次打席の開始）に差し掛かったとき。  
   - **決着らしき結果**（三振・ゴロ・飛球・安打・四死球など、運用で定義した終了表記のいずれか）に到達したとき。

4. **限界（ルールを足しても直らないもの）**  
   - 取得 HTML に **決着行がそもそも存在しない**（JS 後描画のみ・別 XHR・欠損）場合、次行スキャンでは補正できない。  
   - **簡易一覧（例: 球番の右の短い結果列）**を併用する場合も、**上記と同じ打席境界**で解釈する（別ブロックだからといって無制限にマージしない）。

### §6b. 簡易表（球番・各球結果）×「ボール／ストライク」末尾 → **「次へ」必須**（運用規定・2026-04）

**対象 UI（用語の固定）**

- **本表**: 「詳しい投球内容」内の `bb-splitsTable`（球種・球速・結果の縦表）。実装では複数ブロックを DOM 順に結合。
- **簡易表**: 同ブロック付近の **2 列だけ**の「球番（投球数）｜結果」一覧（`scripts/scrape_yahoo_pitch_details.py` の `_parse_two_column_pitch_index_pairs` が読む形式。画面上は本表の下側に出ることが多い）。

**問題の整理**

- 走者イベントや表示分割により、**本表の最終行だけがカウントの途中**に見えることがある。
- そのとき **Yahoo の画面上は「次へ」**で同一打席の続きページに進むと **決着が現れる**一方、**1 ページだけ取得している derived では欠行・末尾ボールのまま**になり得る。

**中間表記の定義（この節での「ボール／ストライク」）**

| 区分 | 末尾 `result` の例 | 注 |
|------|---------------------|-----|
| **ボール系** | `ボール`、または `ボール[` で始まる | 既存 §6a と同じ |
| **ストライク系（カウント進行のみ）** | **`見逃し`**（単独）、**`空振り`**（単独）、**`ファウル`**（**括弧なし**の素のファウル） | `ファウル[ランエンドヒット]` のように**状況が `[]` 内に付く行は除外**（別扱い） |

**取得（スクレイプ）側の必須動作**

1. **同一打席の score は 1 ページで切らない**  
   - `scripts/run_yahoo_phase10_restore.py` が使う `fetch_pitch_detail_score_pages_for_pa`（`a#btn_next` が **同一 `inning|表裏|bat_order` かつサフィックス昇順**のときのみ追従）を **必ず通す**。  
   - **運用**: Phase10 を叩くときは **常にこの経路**とし、**単一 URL の `…/score?index=…` 1 回だけ**で打席 JSON を作ってよい、と**決めない**（欠行リスクのため）。
2. **本表パース後**、最終行が §6b の中間表記なら、(1) **同一 `tbody` の続き `tr`**、(2) **簡易表で欠番の球**を追補する（`_extend_pitch_rows_after_ball_trailing`。実装上はボールだけでなく §6b のストライク進行のみも同じトリガ）。  
   - **それでも決着が出ない**ときは **未取得の続きページが残っている**可能性が高い → **Phase10 再取得**（ネットワーク許可・レートは既存どおり）。

#### 取得「完了」の定義と運用（いつ derived を確定してよいか）

**「ボール／ストライク（§6b の中間）で末尾が終わっている」ときは、`次へ` を見切れていないか／欠行がないかを疑う。**  
単にログに残すだけでなく、**次工程では次のように扱う**（以降この前提で Phase10 を叩く）。

| 条件 | 意味 | 次にやること（デフォルト） |
|------|------|---------------------------|
| **マージ前**：fetch＋パース後の**最終 `result` が §6b の中間** | 当該打席は **一球としては未取得または不完全** とみなす | `run_yahoo_phase10_restore.py` が `missingOrPartial` にタグを付与する（下表）。**その derived を「取れた」として canonical マージだけで締めない**ことを運用で固定する（再取得・ブラウザ確認・§6c）。 |
| **`trailing_intermediate_single_page_next_required`** | **1 ページだけ**（`btn_next` を 0 回）で末尾が中間 | **最優先で「次へ」追従漏れ**の疑い。再実行・レート調整のうえ **同一経路で再取得**。ブラウザで当該 `score?index=` を開き **次ページに決着があるか**を確認。 |
| **`trailing_intermediate_after_multi_page`** | **複数ページ取得後**も末尾が中間 | **追従はしたが決着が HTML に無い**疑い。簡易表・本表の結合・イベント後の欠行を疑い、**§6c の帳票照合**へ進む（捏造・regex 先での確定は禁止）。 |

**§6c との役割分担**：§6b は **一球 UI 上の「次へ・表の網羅」**まで。§6c は **帳票（公式・出場成績）と一球の食い違い**を見つけたあとの **再取得・手戻り手順**。§6b のタグは **ソース側で中間末尾が残った事実**を機械可読に残し、§6c は **外データと突き合わせたときのエスカレーション**に使う。

**マージ（canonical）側の必須動作**

- `lib/yahooGame/mergePhase10FromPitchRows.ts` の `pickResultSummaryJaFromPitchRows`：**末尾がボール系だけでなく §6b のストライク進行のみの行**が続くときも、**同一打席内の直前の非中間行**を `resultSummaryJa` に使う（**欠行時は従来どおり直らない**）。

**レビュー・運用チェックリスト（以降の PR / 試合取り込みで確認）**

- [ ] Phase10 出力に **同一打席で複数 `index`（ページ数 >1）が取れているか**（ログ `(Np)` 等）— **該当する打席が多い日ほど重要**  
- [ ] 疑わしい打席（本表末尾が **ボール** / **ボール[** / **見逃し** / **空振り** / 素 **ファウル**）は **ブラウザで「次へ」1 画面先に決着があるか**をスポット確認し、**derived に最終球が乗っているか**を見る

### §6c. 公式記録と一球ログが食い違うとき（**再取得を運用上必須とする**・手戻り禁止の手順）

**読み先**: スポーツナビの **出場成績・打席結果**（または NPB 公式の当該打席短文）を「帳票上の正」とし、Yahoo **一球ログ（Phase10 の `result` 列）**と **対応付けて**矛盾を見つける。**一球だけを正にしてよいわけではない**（§2 冒頭のデータソース方針と同じ）。

#### 1. 再取得を「必須」とみなすトリガ（例）

次の**いずれか**を満たしたら、**その試合の Phase10 は再取得前の derived を正として確定しない**（マージ済み canonical があっても **再取得 → 再マージ**を優先）。

| # | 状況（例） | 意味 |
|---|-----------|------|
| A | 帳票上その打席が **一ゴロ**／**内安** 等なのに、当該 `inning|表裏|bat_order` の Phase10 行に **`一ゴロ` 等の決着語が1行も無い** | HTML 欠け・`btn_next` 未辿り・表結合漏れの疑い |
| B | §6a・§6b のマージ後も `resultSummaryJa` が **中間表記だけ**（末尾がボール系／§6b のストライク進行のみのまま等） | 決着行が derived に無い |
| C | **桑原（`yahoo_1100061`）と同一人物・同一試合**で、議論のあった **2026-04-18 `gameId=2021038735`・5回表・攻撃の該当打席**のように、**手元の `*_phase10_restored.json` に当該選手の `一ゴロ` が一度も現れない**が、公式は一ゴロである | **再取得して still 無ければ**ソース限界扱い（下記エスカレーション） |

※ C は **データ検索で再現可能**な具体例として置く（「存在しないこと」の確認は `batter_id` と `result` を grep）。

#### 2. 必須の実務手順（次回からこの順で止めない）

1. **ネットワーク付きで Phase10 を再取得**  
   - `python scripts/run_yahoo_phase10_restore.py --game-id <試合ID>`（運用どおり `--sleep` 等）。  
   - **単一 score URL だけを手で叩いて 1 ページだけ保存**した JSON を成果物に**しない**（§6b）。
2. **再マージ**  
   - `npm run phase4:merge:phase10` またはバッチ手順で canonical を更新。
3. **まだ決着行が無いとき**  
   - **コードで「一ゴロ」と文字列代入してごまかさない**。  
   - `game.missingOrPartial` 等に **「Phase10 に公式と整合する決着行なし」**を残す、または別チケットで **手入力上書き・公式 API** を検討。  
   - 自動テストに **「公式=一ゴロ」を期待する**場合は、**再取得後の Phase10 スナップショットに `一ゴロ` 行が実在すること**を前提にする。欠けたままの fixture で期待 **一ゴロ** は **テスト設計ミス**（失敗が正しい）。

#### 3. 期待値テストのルール

- **正当性**: 「公式と同じ」結果を assert するテストは、**入力データが公式と整合するスナップショット**（再取得後 derived）であることを **README／コメントで明記**する。  
- **否認**: 手元に **一ゴロ行が無い** derived のまま「桑原の打席は一ゴロ」を期待するテストは **採用しない**（再取得かデータ差し替えが先）。

### 集計コード側の位置づけ

- 本件は **データ欠損・`resultSummaryJa` の誤り**の問題。`hitBases` / `isAtBat` のパターン追加だけでは解決しない。**§6c の齟齬は再取得・エスカレーションが先**。
