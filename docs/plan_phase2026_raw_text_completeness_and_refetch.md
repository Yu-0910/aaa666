# 計画書: 2026 シーズン raw テキストの「未開催・試合前スナップショット」と「充足済み」の区別と再取得（フェーズ整理）

## 0. 目的

- `_data/scraped_games/raw_sportsnavi_text/{gameId}.html` を、**パイプライン上「Phase2 でパース可能」とみなす基準**で二分する。
  - **未充足**: 試合前・未開催・本文未掲載などで **`bb-liveText` が存在しない** → **再取得（HTTP）必須**。
  - **充足済み**: **`bb-liveText` が存在する** → 現時点の基準ではテキスト raw は**再取得不要**（下流の再計算のみでよいケースがある）。
- 上記を **本計画フェーズ 1〜5**（後述）に落とし、再取得コストと検証コストを最小化する。

### 0.1 番号の読み方（初心者向け）

この文書には **2 種類の「番号」** が出てきます。**混同しない**のがポイントです。

| 種類 | 表記の例 | 意味 |
|------|----------|------|
| **本計画フェーズ** | **フェーズ 1**、**フェーズ 2**、…、**フェーズ 5** | **この計画書だけ**の手順番号。**自然数 1 から順に増える**。「いまどの作業段階か」を表す。 |
| **npm／リポジトリの通称** | `phase0`、`phase1`、`phase2:sportsnavi:stats-text`、`phase10` など | **コマンド名やフォルダ運用で使っている名前**。数字は **飛び番**（0,1,2,4,10…）で、**本計画フェーズ 1〜5 と一致しません**。 |

**覚え方:** 「**フェーズ 3**」と書いてあれば計画の段階。「**Phase2b**」と書いてあれば `npm run …` の名前、と読み分ける。

## 2. 区分基準（SSOT）

### 2.1 未充足（要再取得）

次のいずれかを満たす `gameId` を **「未充足」** とする。

1. `raw_sportsnavi_text/{gameId}.html` が存在しない、または  
2. ファイル先頭付近に `FETCH_FAILED` 等の取得失敗マーカーがある、または  
3. **本文判定**: 文字列 `bb-liveText` が **0 件**（`class="bb-liveText"` を含まない）

> 注: 中止試合は試合トップ HTML の判定で「空でも完了」と扱う分岐がある（`phase2_fetch_sportsnavi_stats_text.mjs`）。本計画の「未充足」は主に **開催予定カードの試合前スナップショット** を想定する。

### 2.2 充足済み（テキスト raw は再取得不要の候補）

- `raw_sportsnavi_text/{gameId}.html` に **`bb-liveText` が 1 件以上**ある。

このとき **公式確定やサイト側の後追い修正**まで含めて「正しい」とは限らないが、**「試合前の空シェル」問題は本基準では除外**できる。

## 4. 本計画フェーズ 1〜5（実行手順・自然数のみ）

全体の流れは **1 → 2 → 3 → 4 → 5** の **5 段階**です。前の段が終わってから次へ進むと安全です。

```
フェーズ1（診断・リスト） → フェーズ2（再取得） → フェーズ3（下流更新）
    → フェーズ4（検証） → フェーズ5（再発防止ルール）
```

### フェーズ 1 — 診断の固定化とリストの SSOT 化

**目的**: 手作業と口頭の「11 試合」を、**再現可能な成果物**にする。

| 小番号 | 内容 |
|--------|------|
| 1-1 | プロジェクトルートで `npm run diag:phase2-raw-completeness` を実行し、JSON を `_data/reports/` 等に保存する。 |
| 1-2 | 出力の `incompleteGameIds` と、本計画 §3 のリストを突合し、**差分があれば §3 を更新**する。 |
| 1-3 | （任意）`raw_stats_href_player_count` が極端に低い試合を「テキスト未充足と独立に」フラグ化し、**フェーズ 3** の前に **Phase2a** の stats 再取得対象に含めるか判断する。 |

**完了条件**: `incompleteGameIds` がファイル化され、コミットまたは運用メモに紐づく。

---

### フェーズ 2 — 未充足キューに対する差分再取得（Phase2a）

**目的**: **充足済み 111 試合には触れず**、未充足候補だけ HTTP で取り直す。

| 小番号 | 内容 |
|--------|------|
| 2-1 | 対象試合が **実施済み（テキストが載る状態）**であることを確認する（公式日程・試合結果ページの確認）。未実施なら再取得しても未充足のままなので **日付をずらして再実行**する。 |
| 2-2 | `node scripts/phase2_fetch_sportsnavi_stats_text.mjs --year 2026 --game-ids <カンマ区切り> --force` で **該当 gameId のみ** stats + text を再取得する。 |
| 2-3 | 広範囲で取り直す場合は `--only-incomplete`（既存ロジック: 選手リンク不足・`bb-liveText` 不足）を使い、**全件 `--force` より優先**する。 |

**完了条件**: **フェーズ 1** で確定した `incompleteGameIds` がすべて **§2.2 の充足済み**に変わる（または「未実施のため保留」と明示）。

---

### フェーズ 3 — 下流の再生成（Phase2b → Phase4 準備 → Phase10 → 派生）

**目的**: テキスト raw が変わった試合について、**canonical 以降を整合**させる。

| 小番号 | 内容 |
|--------|------|
| 3-1 | **Phase2b**: `npm run phase2:sportsnavi:canonical -- --game-ids ...` または該当年の `--force` 範囲で canonical を更新する。 |
| 3-2 | **Phase4 準備**: `node scripts/phase4_prepare_yahoo_phase10_text_from_sportsnavi_raw.mjs --year 2026 --force`（対象試合のみにしたい場合はスクリプト拡張または手動コピー方針を決める）。 |
| 3-3 | **Phase10**: 変更試合のみ `run_yahoo_phase10_restore.py` と `merge_yahoo_phase10_canonical.ts` を実行する（既存の `phase4_yahoo_pitch_by_pitch_pipeline.mjs` や `npm run phase10:yahoo:restore` の運用に合わせる）。一球が不要ならスキップ可。 |
| 3-4 | **派生・ランキング**: `npm run phase3:derived:2026` および `npm run rankings:rebuild`、または `npm run phase3:derived:2026:and-rankings` 等、運用ドキュメントに沿って実行する。 |

**完了条件**: 変更のあった `gameId` について `canonical` と `derived` の更新日時・内容が一致し、既知の欠損フラグが消えている。

---

### フェーズ 4 — 検証ゲート

**目的**: 「区別がついたまま正しく直った」ことを証明する。

| 小番号 | 内容 |
|--------|------|
| 4-1 | **フェーズ 1** と同じ `diag:phase2-raw-completeness` を再実行し、`incompleteCount === 0`（中止等の例外を除く）を確認する。 |
| 4-2 | 代表 2〜3 試合で、**テキスト HTML にイニング見出し・打席ブロック**が含まれることを目視する。 |
| 4-3 | （任意）既存の `npm run validate:*` で打席・ランキングの整合を確認する。 |

### フェーズ 5 — 再発防止（運用ルール）

**目的**: 同じ「試合前スナップショットが未充足として残る」状態を減らす。

| 小番号 | 内容 |
|--------|------|

## 6. リスクと注意

- **再取得しても未充足のまま**: 試合が **降雨中止・ノーゲーム・未開催**のまま。対処は「保留」とし、**実施後にフェーズ 2 を再実行**する。
- **111 試合は再取得不要（基準上）**だが、**サイトの後追い修正**で数値だけズレることはあり得る。その場合は **Phase2b のみ `--force`** でよい（HTTP 不要の可能性）。
- **Phase5 型パイプライン**（`phase1` の直後に `phase2:sportsnavi:canonical` のみ）だと **Phase2a が抜ける**。本問題とは別だが、運用ミス防止のため **日次パイプラインまたは `phase2:sportsnavi:stats-text` を必須ステップ**と明記する。
