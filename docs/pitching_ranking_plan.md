## 1. 目的・スコープ

- **目的**: 既存の野手（打撃）ランキングページと**同一の構成・UI**で、**投手成績**のランキングページを提供する。
- **差分**: 表示する**指標の一覧・順序・ソート既定**のみ。ルーティング階層・テーブルレイアウト（`RankingUI` 相当）、英字名補完・規定考慮の考え方は野手側と揃える。
- **UI で明示したい仕様**（本書に詳述）:
  - **§2.1** … メイン見出し（例: `セ・リーグ　防御率ランキング (2026年)`）
  - **§2.2** … 選手列（**球団帯＋和名＋英字名**の1セット）
  - **§3.1** … 2026 トップの投球成績から完成品 URL への導線（別作業）
  - **§3.2** … 一覧表示のデータ流れ（事前 JSON＋クライアントで規定・ソート・順位付け直し）
- **対象年度（完成品）**: **2026 年のランキングのみ**を掲載する。他年度のデータ配備・URL での参照・年度切替 UI は**行わない**（`/ranking/pitching/2025/...` 等は `notFound` または 2026 へ誘導するなど、実装時に一本化）。
- **非スコープ（初版）**: 投手専用のデザイン刷新、打撃ランキングの `Record.csv` との列共有、2026 以外の年度別ランキング。

### 1.1 データ取得範囲（段階的拡張）

| 段階 | 方針 |
|------|------|
| **当面（第1段）** | canonical／派生の入力は **広島対中日の1試合（現行 PoC 試合）のみ**とする。投手ランキング JSON も **当該試合に登場し記録が付く選手**が中心となり、**セ・リーグ全試合・全選手は対象外**。 |
| **第2段（以降）** | **正確性・パイプラインの検証が取れたら**、取得対象を **全試合（またはシーズン全体のデータソース）** に拡張する。本書の UI・URL・指標仕様は維持し、**入力ディレクトリ・スクリプトの対象ファイル一覧**を広げる形で移行する。 |

第1段のうちは、ランキングページ上に **「本ランキングは○試合分のデータに基づく」** 等の注記を出すかどうかは実装時に決める（ユーザー誤解防止に有効）。

### 1.2 正確性担保と個別ページ検証→汎用修正の原則

正確性の担保のため **特定の投手の個人ページ**を見ながら微調整を繰り返す想定である。その際、**同じ誤りを別選手で繰り返さない**よう、次を計画レベルで守る。

| 原則 | 内容 |
|------|------|
| **検証の入り口** | 不具合・数値の違和感は **1人の個人ページ**で発見してよい（再現手順・URL・期待値を残す）。 |
| **修正の置き場所** | 修正は **その選手 ID 専用の分岐に閉じない**。可能な限り **共通コードパス**に置く：`app/players/[playerId]/page.tsx` 内の投手共通 UI、`SeasonStatsPilot` / `PitchDetailsPilot`、対応する **`app/api/...`**、`lib/` の正規化・マージ、**canonical 取り込み／Phase スクリプト**、ランキング JSON 生成ロジックなど。 |
| **禁止に近いパターン** | 特定 `npb_player_id` / Yahoo ID だけで表示や API 応答を変える **1点物の if**（他投手で再発し、メンテ不能になる）。例外的に手動マップが必要な場合は **`MANUAL_YAHOO_TO_NPB` のような集中した表**に限定し、理由をコメントで残す。 |
| **汎用性の確認** | 修正後、**別の投手個人ページ（名簿上の別名・別球団）で最低1件**スポット確認する。ランキング側に影響する変更なら **ランキング表の別行**でも確認する。 |
| **知識の残し方** | 修正ごとに **なぜバグが起きたか／どこを直したか**を短く残す（コミット本文、本書の改訂履歴、または `docs/` 内の運用メモのいずれか。ユーザーが別途 `data_operation_rules.md` 等を持つ場合はそちらへリンクしてもよい）。 |

**ランキングページ完成後も同様**：ランキングで1行おかしいと気づいたら、行の選手だけ特別扱いせず、**指標計算・JSON スキーマ・マージルール**を直し、全行が同じルールで再計算されるようにする。

### 2.1 ランキング一覧ページのメイン見出し（打撃と同一形式）

指標ごとのランキング表が表示される画面では、打撃ランキング（`components/RankingUI.tsx`）と**同じ規則**で **H1 タイトル**を出す。

| 項目 | 仕様 |
|------|------|
| **形式** | `《リーグ表示名》　《選択中の指標ラベル》ランキング (《年度》年)`（全角スペース `　` は打撃 UI と同様） |
| **打撃の例** | `セ・リーグ　OPSランキング (2025年)` |
| **投手の例** | `パ・リーグ　防御率ランキング (2026年)`、`セ・リーグ　WHIPランキング (2026年)` |
| **指標名** | 現在のソートキーに対応する `MetricDefinition.label`（§2 の表示ラベルと一致） |
| **リーグ名** | `CL` → `セ・リーグ`、`PL` → `パ・リーグ`。春季・秋季等を扱う場合は打撃ランキングの `page.tsx` と同じ表示名マッピングに揃える |
| **年度** | 完成品は **2026** のみだが、表示は `(2026年)` と括弧付きで野手と同型にする |

**実装方針**: 投手ページでも **`RankingUI` をそのまま利用**するか、同一ロジックを共有し、**`displayTitle = \`${leagueName}　${metricLabel}ランキング (${season}年)\`** を再現する。指標をクリックして切り替えたときは **見出しの指標名だけが差し替わる**（打撃ページの挙動と一致）。

### 2.2 選手名表示（1セットのルール）

各順位行の「選手」ブロックは、打撃ランキング（`components/RankingUI.tsx`）と**同一の見た目・構造**とする。**和名＋英字名＋球団帯カラー**を**ひとまとまり**（1セット）として表示する。

| 要素 | 仕様 |
|------|------|
| **球団帯** | 選手名の左に **縦のカラーバー**（`w-1 h-8` 相当）。色は行の **`team`**（チームコード）をキーにした **`teamColors`** マップ（`RankingUI` 内）で決定。未マッチ時はフォールバック色（現状 `#fff` に近い扱い） |
| **和名** | **`name`** を表示用に **半角・全角スペース除去**（`replace(/\s+/g, '')`）。太字・白・ホバーで黄系（打撃と同じクラス） |
| **英字名** | **`romanName`** があるときのみ、和名の**下**に小さめグレー文字（`latin`、約 10px）。表示前に **`formatRomanName`**（イニシャル付き略式など、打撃と同一関数）を適用 |
| **リンク** | 和名を **`/players/{playerId}`** へ。クエリに `name`、英字がある場合は `roman` を付与（打撃と同じ URL 規則） |
| **データ** | 各行 JSON に **`playerId` / `name` / `team`** を必須、`romanName` は任意。英字が欠ける場合は **クライアント側で `/api/roman-names/...` マージ**する流れを打撃の `RankingPageClient` と揃えてもよい |

**まとめ**: **順位列の右・指標列の左**にある選手セルでは、左から **帯（球団色）→ 和名（リンク）→ その下に英字** が1セット。投手ランキングも **`RankingUI` 共有**でこのルールをそのまま満たすのが望ましい。

## 3. 既存資産との対応関係（打撃ランキング）

| 領域 | 打撃（現状） | 投手（本計画） |
|------|--------------|----------------|
| URL | `/ranking/[year]/[league]` | **`/ranking/pitching/[year]/[league]`**（**完成品で有効なのは `year=2026` のみ**。例: `/ranking/pitching/2026/PL`） |
| 指標の「正」 | `Record.csv` 先頭行 + `loadMetricsFromRecord` | **`Record_pitching.csv`**（または `PitchingRecord.csv`）を新設し、**同じ `MetricDefinition` 形**で読む |
| ランキング JSON | `public/data/rankings/{year}/{season}/{metric}.json` | **`public/data/rankings/pitching/2026/{season}/{metric}.json` のみ**を本番想定で配置（他年度フォルダは作らない） |
| プロキシ | `app/data/rankings/[...path]/route.ts` | **`pitching` セグメントを解決**するよう拡張、または **`app/data/rankings-pitching/[...path]/route.ts`** を追加 |
| UI | `RankingPageClient` + `RankingUI` | **同一コンポーネントを再利用**。`metrics` を投手用に。**H1 は §2.1**、**選手表示は §2.2**（帯＋和名＋英字の1セット）。`viewModel.title` は初期値・メタ用に留めてもよい |
| **一覧のデータ流れ** | 指標ごと JSON を fetch → クライアントで規定・ソート・`rank` 再計算（野手と同型） | **§3.2** に詳述。**表示順は JSON ファイル内の並びに依存しない**。 |
| 規定 | `qualifyingPA`（打席） | **投球回・登板数など**の規定を別モジュール（例: `qualifyingPitching.ts`）で定義 |

### 3.1 トップページから完成品へ（別作業として必須）

**投手ランキングページの実装だけでは、2026 年トップの投手指標から完成品は表示されない。**  
現状、トップの「セ/パ 投球成績」は `app/components/top/TopPagePanels.tsx` の **`LeadersPanel`** が **`getStatsListUrl()` で `/ranking/${year}/${league}`**（**打撃ランキング**）へ遷移させている。指標名の **`getRankingUrl()`** も同じ打撃用パス・野手向け `metric_map.json` 正規化に依存している。

完成品をトップから開くには、次を**ランキングページ本体とは別タスク**として行う。

- [x] **「成績一覧」**: 投球成績パネル（`getDataForPanel(..., "pitching")` を渡す `LeadersPanel`）のみ、リンク先を **`/ranking/pitching/2026/{CL|PL}`** に変更する（完成品は 2026 のみのため、年度セレクトが 2026 以外のときの挙動は仕様で固定する：例・非 2026 では投手「成績一覧」を無効化・別案内・または打撃 URL のまま等）。
- [x] **指標名クリック**: 投手パネル用に `getRankingUrl` を分岐し、**投手ランキングのクエリ**（`?sort=` 等）と **投手 JSON の指標キー**・ソート昇降が一致するようにする（野手用キーと混線しないこと）。
- [x] **ヘッダー「成績一覧」**（`TopPageClient` の `rankingHref` 等）が打撃専用のままか、投手用リンクを別設するかを決め、必要なら導線を追加する。
- [x] `TopPageMobileDrawer` など、同一 URL パターンのリンクがあれば同様に確認する。

### 3.2 表示時のデータ流れ（事前 JSON とクライアント側処理）

野手ランキング（`RankingPageClient`）と**同じ表示の仕方**を投手でも採用する。計画上、次を明確にする。

| 段階 | 内容 |
|------|------|
| **事前準備** | 指標ごとに **JSON ファイル**（例: `防御率.json`）を配置。行には **選手ごとの各指標の値**を載せる。パイプライン側でソート済みにしてもよいが、**表示順の唯一の正とはしない**。 |
| **ページ表示** | 現在の `sort`（指標キー）に対応する **1 本の JSON を fetch**（野手の「案A」と同様）。 |
| **ブラウザ側** | 取得した行に対し、**規定（クオリファイ）でフィルタ** → **選択中の指標列でソート** → **`rank` を付け直す**。これにより、**JSON に書かれた順序や rank をそのまま信頼しない**。 |
| **負荷** | 行数が数百〜千程度ならメモリ上のソートは軽量。ボトルネックは主に **fetch と JSON サイズ**。 |

投手版も **`RankingPageClient` をコピー改変**する前提なら、上記は**追加実装なしで自然に踏襲**される。仕様変更で「JSON の順序をそのまま表示」にしたい場合は、本節と実装の両方を改めること。

## 4. Phase 別タスク

### Phase 0 — 仕様固定

- [ ] 各指標の**データ型**（率 / 回数 / 整数）と**ソート方向**（昇順・降順）を表に落とす（防御率・WHIP・被打率等は昇順、勝利・三振等は降順など）。
- [ ] K-BB％、P/IP、QS/HQS/SQS の**計算式**をデータパイプライン側のソース（公式定義 or 自前定義）で一文固定。
- [ ] `HP` の意味（保持 / ヒット許容など）をデータ列と照合。

### Phase 1 — 指標マスタと型

- [x] リポジトリ直下または `_data/master_csv/` に **`Record_pitching.csv`**（1行目＝指標名、ユーザー指定順）を置く。（**ランキング用の正は `_data/master_csv/Record_pitching.csv`**＝§2 の日本語 30 指標。ルートの英語ヘッダーは既存 Python 用として維持。）
- [x] `lib/ranking/recordPitching.ts`: `loadMetricsFromRecordPitching()` で `MetricDefinition[]` を返す（`record.ts` と同様の除外列・正規化ルール。読み取り優先は `_data/master_csv/` → ルート）。
- [x] `config/pitching_metric_map.json` と `lib/ranking/metricMap.ts` の **`getPitchingJsonKey` / `loadPitchingMetricMap`** で、CSV 列名 → **JSON キー**を対応付け（ルート CSV 用の英語エイリアスも同ファイルに含む）。

### Phase 2 — データパイプライン（JSON 生成）

- [x] **§1.1** に従い、**第1段は `_data/scraped_games/canonical/*.json` にある試合のみ**を集計対象とする（現状 PoC は 1 試合）。全試合拡張時は canonical を追加するか、スクリプトの入力ディレクトリを差し替え可能な設計にする。
- [x] 投手成績の入力形式: **`domain.pitchingLines`**（`PitchingLine`）を試合内で投手 ID ごとにマージし、試合間で合算。セーブ・先発・QS 系など canonical に無い項目は **0**（将来パイプライン拡張）。
- [x] 指標ごとにランキング JSON を出力するスクリプト **`scripts/phase19_build_pitching_rankings_from_canonical.ts`**（`npm run phase19:build:pitching-rankings`）。**§3.2** に合わせクライアントが再ソートするが、ファイル内は指標ごとにソート済みでもよい。各指標で **`{label}_all.json` も出力**（野手と同型）。
- [x] 出力先: **`public/data/rankings/pitching/2026/{CL|PL}/{sanitize(label)}.json`** のみ（**2026 以外はスクリプトが拒否**）。
- [x] `package.json` に **`phase19:build:pitching-rankings`** を追加。

### Phase 3 — 取得経路（URL・ローダー・プロキシ）

- [x] `lib/ranking/jsonLoader.ts`: **`loadPitchingRankingJson` / `loadPitchingRankingJsons`** を追加。URL は **`/data/rankings/pitching/{year}/{season}/{file}`**。**2025 フォールバックは行わない**（打撃の `loadRankingJson` と差別化）。
- [x] `getRankingsUrl` / `RANKINGS_EXTERNALIZE_SCOPE`: 投手パスは `data/rankings/pitching/...` のため、既存の部分一致ロジックでそのまま扱える旨を **`lib/ranking/url.ts` の JSDoc** に記載。
- [x] `app/data/rankings/[...path]/route.ts`: **`pitching/年/リーグ/…` が `public/data/rankings/` 直下の相対パスとして解決される**既存挙動を利用。コメントで投手パスと打撃の 2026→2025 フォールバック差を明記。

### Phase 4 — ページ・ルーティング

- [x] `app/ranking/pitching/[year]/[league]/page.tsx`: 打撃をベースに **`loadMetricsFromRecordPitching()`**。**`RankingUI` の見出し**で §2.1 同型（`セ・リーグ　《指標》ランキング (2026年)` 等）。
- [x] **選手列 §2.2**: `RankingUI` 共有。**`PitchingRankingPageClient`** で `mergeRomanNamesFromCsv` 相当を実装。
- [x] **`year !== '2026'` は `notFound()`**。
- [x] **`PitchingRankingPageClient.tsx`**: `loadPitchingRankingJson`、既定 **`sort=era`**、**`getPitchingSortOrderForKey`**（`lib/ranking/pitchingSortOrder.ts` とトップ導線で共有）、§3.2 のフィルタ・ソート・`rank` 再計算。規定は **`lib/ranking/qualifyingPitching.ts`**（Phase 4 は閾値 0 で実質スキップ）。
- [x] **`components/RankingUI.tsx`**: `rankingPathBase`・`metricLabelFallback`・**`yearOptions`**（投手は `[2026]` のみ）を追加。
- [x] `/ranking` インデックスからの導線・トップ連携は **Phase 6（§3.1）**（トップ・ドロワー・投球パネルで投手ランキングへ）。

## 5. リスク・注意点

- **データ未準備**: JSON が無い指標は UI 上タブは出るが取得失敗する。Phase 2 で最低限 CL/PL・主要指標から順に埋める（**すべて 2026 配下**）。
- **年度スコープ**: 完成後も **2026 のみ**と明確にし、将来ほか年度を載せる場合は別フェーズで URL・データ・本書を改訂する。
- **指標名のファイル名**: 日本語・記号混在は `sanitizeMetricForPath` で一意化され、**ビルドスクリプトと同一ルール**であること。
- **重複**: 打撃 `Record.csv` と列名が衝突する場合は、投手用マスタを完全分離して混線を防ぐ。
- **トップ連携の漏れ**: §3.1 を実装しないと、ユーザーは投手指標の「成績一覧」で**打撃ランキング**に着地し続ける。
- **単試合データ（§1.1 第1段）**: ランキングは **1試合由来**のため順位・値はリーグ全体の公式成績とは一致しない。UI またはドキュメントで期待値をずらさないこと。
- **個別ハードコード（§1.2 回避）**: 1選手だけの特別分岐が増えると、他投手で同種バグが再発し検証コストが爆増する。

## 6. 完了の定義（Definition of Done）

- **`/ranking/pitching/2026/{league}`**（およびインデックスからのリダイレクト）で、野手ページと同様にテーブル・指標ヘッダー・ソートが動作する。
- ランキング一覧の**データの取り扱い**が **§3.2**（事前 JSON＋クライアント側の規定・ソート・順位再計算）と一致していること。
- メイン見出しが **§2.1** の形式になっており、指標切替で **「《リーグ》　《指標》ランキング (2026年)」** が打撃ランキングと同様に更新される。
- 選手列が **§2.2** のとおり、**球団帯カラー＋和名＋英字名**が打撃ランキングと同一ルールで表示される。
- **2026 年以外のパス**では掲載されない（`notFound` または 2026 へ統一）。
- 上記 **30 指標**がマスタ順で表示され、**2026 年・対象リーグ**でデータが参照できる。
- 投手用 JSON の生成手順がドキュメントまたはスクリプトで再現可能（**出力先は `pitching/2026/` のみ**）。
- **§3.1** に従い、**2026 年トップの投球成績**から「成績一覧」および指標リンクで**投手ランキング完成品**が開くこと。
- **§1.1 第1段**ではデータが **1試合分**に限られることを理解したうえでの動作（全試合拡張後は DoD の期待値を更新する）。
- 正確性に関する修正は **§1.2** に沿い、**全投手（およびランキング全行）に効く形**で入っていること。
