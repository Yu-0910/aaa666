# 2026年 NPB 全試合日程 取得・監視計画（スポナビ起点）

目的: **NPB 全試合の試合情報を取りこぼさず取得**し、雨天中止などで **後日追加される日程も確実に拾う**。取りこぼした場合は **即座に気づける**運用を用意する。

前提:
- 日程・結果の一次ソースはスポナビ（Yahoo! JAPAN / Sportsnavi）とする。
- 取得対象は「1軍」「リーグ戦 / 交流戦 / CS / 日本シリーズ」（必要ならオープン戦も同様に）。

参照URL例（リーグ戦）:
- `https://baseball.yahoo.co.jp/npb/schedule/first/league?date=2026-03-27`

---

## ゴール（何を満たせば成功か）

- **全日付**について、スポナビ上に存在する「試合（実施/中止/延期/ノーゲーム含む）」を **ユニークに記録**できる。
- **中止・延期**になった試合は、その後 **再編成された新しい日程（9月以降など）**で再度現れたときに **差分として検知**し、DB/JSONに反映できる。
- 取得漏れが起きた場合、**翌日までに**（できれば当日）アラート相当で発見できる。

---

## 取得データの正規形（これだけあれば追跡できる）

スポナビ日程ページから最低限、次の正規形を作る（保存先は `_data/sportsnavi_schedule_snapshots/` など）。

### 1) ゲームのユニークキー（推奨）

- **gameId**（スポナビの試合ページURLに含まれるID）を最優先キーとする  
  例: `.../npb/game/2021038624/index` → `2021038624`

スポナビに gameId が必ずあるため、同一試合の重複排除・状態遷移追跡ができる。

### 2) 保存するフィールド（例）

- `gameId`
- `gameDateJst`（YYYY-MM-DD）
- `leagueKind`（CL/PL/interleague/…）
- `status`（scheduled / in_progress / final / cancelled / postponed / no_game など）
- `homeTeamName` / `awayTeamName`
- `stadiumName`（取得できる場合）— **実装済み（2026-05）**: Phase 0 が日程表 `bb-scheduleTable__stadium` 列をパースし、`by_date/*.json` の `games[]` / `stadiumByGameId` と `season_YYYY.json` の `stadiumByGameId` に保存。Phase 13 球場別打撃はこれを参照（`fetch:yahoo-game-meta` の score ページは球場名には使わない）。
- `homeScore` / `awayScore`（取得できる場合）
- `note`（「中止」「ノーゲーム」「雨天」等の文字列）
- `sourceUrl`（当日のスポナビ日程URL）
- `fetchedAt`

## 取得戦略（取りこぼし防止の要点）

### A. 取得対象日付の作り方（カレンダー共有を前提）

ユーザーが共有する「今季カレンダー」を正とし、**その全日付を必ず巡回**する。

- 例: `season_calendar_2026.json`（開始日～最終想定日）
- 毎日、当日+前後のバッファで巡回（後述）

### B. 巡回ウィンドウ（中止→再編成に強くする）

スポナビ上の日程は「過去」「当日」「未来」で更新されるため、**同じ日付を繰り返し取りに行く**。

推奨（運用）:
- **毎日**:
  - `D-2, D-1, D, D+1, D+2` を取得（試合開始前後・結果反映の遅延に強い）
  - さらに `D+30` までの未来を **週1**で総なめ（将来の再編成を早期発見）
- **9月以降（再編成が増える時期）**:
  - 未来総なめを **週2**へ増やす

### C. スナップショットを必ず保存する（差分検知のため）

「その日のHTML→パース結果」を保存しておくと、後から
- スポナビ側の表示差
- パーサのバグ
- 取りこぼし
を特定しやすい。

保存単位:
- `byDate`: `YYYY-MM-DD.json`（当日取得の正規化結果）
- `rawHtml`（任意）: `YYYY-MM-DD.html`（容量が許せば）

## 状態遷移（中止・延期・追加日程を拾う）

ゲームは次の状態遷移を取り得る:

- `scheduled` → `in_progress` → `final`
- `scheduled` → `cancelled`（中止）
- `scheduled` → `postponed`（延期）
- `postponed` →（後日）`scheduled`（再掲載）→ `final`

実装上の重要点:
- `gameId` が同一なら **状態更新**として扱う。
- `postponed/cancelled` の試合が、**別の gameId で再出現**するケースがある（再編成で新規枠扱い）。  
  → その場合に備えて「同一カード推定キー」を併用する。

### 同一カード推定キー（gameId が変わる場合の紐付け用）

`(awayTeam, homeTeam, originalDate)` だけだと弱いので、候補として:
- `cardKey = awayTeam + "_" + homeTeam + "_" + stadiumName(optional)`
- さらに `note` に「振替」等があれば利用

運用ルール:
- **gameIdが変わる再編成**は完全自動化せず、差分として抽出し「要確認リスト」に入れる。

## 取りこぼし検知（すぐ気づく仕組み）

### 1) 日別件数チェック（最速で効く）

各日付の取得結果で
- `games.length`
- `league별件数`
を記録し、前回と大きく変わったら「差分アラート」扱いにする。

例:
- ある日だけ 0 件 → パーサ不調/通信失敗の疑い
- 6試合→5試合 → 中止の可能性（正常）だが状態更新が取れているか確認

### 2) 順位表との整合（週次）

スポナビ順位表（勝敗、引分）を取得し、
- 各チームの `勝+負+引` の総和（両リーグ）
と
- `final` 試合数の集計
を突き合わせる（完全一致しない場合は要調査）。

※ 順位表が更新遅延する可能性があるため、週次・または翌日再検算が現実的。

### 3) ゲームID連番/期間穴チェック（補助）

gameId は連番に近いが欠番もあり得るため補助扱い。
ただし「特定期間で gameId が 1件も出ない」などは異常検知に使える。

## 実行計画（今季の運用手順）

### 毎日（自動）

- 取得対象: `D-2..D+2`（5日分）
- 保存: 正規化JSON（+必要ならraw HTML）
- 差分: 前回取得との比較で
  - 新規 gameId
  - status変化
  - 試合開始時刻/球場/カードの変化
を記録

### 週1（自動）

- 取得対象: `D..D+30`（未来の再編成検知）
- 週次整合チェック（順位表 vs final件数）

### 9月以降（手動 or 自動）

- 未来の再編成を拾う頻度を増やす（週2）

## 雨天中止 → 9月以降に追加されるケースの扱い

- 中止が発生した時点で `cancelled/postponed` を記録する（翌日以降の再取得で更新）。
- 未来総なめ（週次）で追加日程を拾い、`new gameId` として検知する。
- `同一カード推定キー` で「中止になったカードが再出現した可能性」をリスト化し、人間が確認して紐付ける。
